ValmenHarness — el recorrido de un ticket, de punta a punta

Quién decide en cada paso, qué cuesta y qué queda grabado. Medido sobre el flujo real de SaiOpenCloud (sept 2026).

Mecánico — código, $0 Modelo evaluador (Jev) — ~$0.0001 Persona — decisión que no se delega Agente de desarrollo (opencode / Hermes)

1 · Nacimiento — del pedido al ticket

~$0.01Pedido del POEn lenguaje natural, desde cualquier cliente MCP. El agente autoriza: read-only hasta que se pida un cambio.
→
$0crear_ticketSe guarda la solicitud literal con su hash. ID: TIPO-MÓDULO-DESC-FECHA.
→
$0gate intake3 checks mecánicos: solicitud preservada, tipo válido, impactos declarados. Aprueba solo.

2 · Análisis — entender antes de tocar

~$0.08Investigaciónbuscar_memoria primero (errores ya conocidos), luego código. Se escribe el Diagnóstico con causa raíz y archivos:línea.
→
$0checks mecánicos¿Los archivos citados existen? ¿La línea citada dice lo que el diagnóstico afirma? Sin modelo.
→
$0.0001Jev evalúa5 proposiciones de hechos verificables. Umbrales: ≥0.90 aprueba, ≤0.10 bloquea, entre medio → humano.

3 · Plan — la compuerta donde la persona sí entra

Plan + criteriosPasos ordenados, criterios de aceptación con <!-- test: … --> o verify: manual, rollback declarado.
→
$0.0001gate planJev puntúa cobertura, coherencia, verificabilidad. Si duda (banda media), escala.
→
Decisión humanaTelegram / Mission Control. Aprueba, rechaza o devuelve — con su frase literal en el recibo. Nunca la escribe el agente.

4 · Implementación y verificación mecánica

~$0.20El agente implementaSolo los archivos del plan. Corre los tests declarados. Registra evidencia con SHA.
→
$0gate qa-mechanicalCorre los test: declarados (prefijos autorizados, timeout configurable), diff limpio, sin secretos, archivos dentro del alcance.
→
Pruebas del POContrato de pruebas entregado: comandos, pasos manuales, ambiente. Estado: awaiting_user_tests.

5 · QA y cierre — nada se marca en falso

Retest con puntosCada hallazgo es un POINT con su propio ciclo (open→…→verified→closed). La confirmación es la frase del PO.
→
$0preparar_cierreRechaza sin consumo de IA registrado. Exige criterios marcados, puntos cerrados, SHAs atribuibles.
→
$0closedRecibo de cierre + consumo medido por sesión (opencode:/hermes:/manual:). Índice regenerado.

6 · Release — lo irreversible nunca se automatiza

proceso deploy8 pasos: preflight, version-check, gate humano, tag, publish, manuales, changelog, notify.
→
Frase literal«APROBAR DEPLOY vX.Y.Z». Sin token para riesgo alto ni impacto en migración/sync/docker. Jamás vía MCP.
ticket: intake → analyzed → planned → approved → in_progress → awaiting_user_tests → in_qa → qa_approved → closed ↘ blocked ────────────────────↗ ↘ changes_requested ↗ point: open → analyzed → in_progress → awaiting_retest → verified → closed release: unreleased → planned → released
Lo que queda en disco de cada decisión: recibo append-only en .valmen/receipts/<ticket>.jsonl con el estado congelado comprimido, las respuestas del modelo, el costo y la decisión humana con su motivo. Una auditoría de hace 3 meses se responde con el archivo, no con una reconstrucción.
